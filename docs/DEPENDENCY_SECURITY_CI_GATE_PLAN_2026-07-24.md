# 依赖安全持续门禁计划（2026-07-24）

## 阶段目标

把上一阶段已经完成的高危依赖修复固化为可重复执行的 CI 门禁，防止后续提交重新引入高危生产依赖、失配锁文件或关闭 TLS 校验。

## 已确认基线

- `backend-node`、`frontweb`、`desktop` 均使用 npm 锁文件。
- 后端回归工作流已使用 Node.js 24 和 `npm ci`。
- 前端端到端与发布工作流仍使用 Node.js 22。
- 发布工作流在两个安装步骤中设置了 `NODE_TLS_REJECT_UNAUTHORIZED=0`。
- `backend-node/.npmrc` 与 `desktop/.npmrc` 设置了 `strict-ssl=false`。
- 2026-07-24 首次调用 npm 官方审计接口返回 HTTP 503；这属于外部审计服务不可用，不能视为审计通过。
- 实际门禁演练发现 `desktop` 仍复制了一组旧版后端运行依赖，生产审计检出 6 个高危、1 个严重漏洞。

## 本阶段范围

1. 新增每个拉取请求及 `main` 推送都会执行的依赖安全工作流。
2. 对三个 Node 子项目执行 `npm ci --ignore-scripts`，以验证清单与锁文件一致性，同时避免 CI 审计阶段运行第三方安装脚本。
3. 使用 npm 官方注册表执行生产依赖审计，高危及严重漏洞使门禁失败；审计服务不可用也保持失败。
4. CI 与发布工作流统一到 Node.js 24。
5. 删除发布流程中的全局 TLS 绕过，并恢复后端、桌面 npm 配置的证书校验。
6. 仅将桌面中与后端重复的高危运行依赖对齐到上一阶段已验证版本，使门禁在当前基线可通过。

## 非目标

- 不升级与本次桌面安全审计失败无关的业务依赖。
- 不修改应用运行时、接口、数据库或前端交互。
- 不部署、不发布安装包。
- 不处理 npm 已提示但尚未造成安装失败的 `better_sqlite3_binary_host_mirror` 配置迁移；该迁移需单独验证桌面原生依赖下载。

## 验收标准

- 自动化策略测试先因缺失门禁失败，再在实现后通过。
- 新工作流 YAML 可解析，并覆盖三个子项目的锁文件一致性检查及生产依赖审计。
- 所有相关工作流使用 Node.js 24。
- 发布工作流与两个 npm 配置中不存在关闭 TLS 校验的设置。
- 后端全量测试、前端测试与构建通过。
- 三个子项目的 npm 官方生产依赖审计通过；若官方接口持续不可用，则 PR 不得宣称审计通过，等待 CI 实际结果。
- PR 上的新增门禁与既有回归检查均通过后才合并。
