# 充值套餐每日赠送积分设计

日期：2026-08-11  
状态：本地实现与自动验证完成；待生产候选和真实支付验收
范围：支付宝充值套餐、租户积分账户、管理员套餐配置、用户充值中心

## 1. 目标

把充值套餐从“基础积分一次到账 + 赠送积分一次到账”改为：

- 套餐售价对应的基础积分一次性到账，永久有效；固定换算为 `1 元 = 100 积分`。
- 原套餐的额外赠送额度改为每日赠送额度，连续 30 个自然日。
- 支付成功当日为第 1 天，以 `Asia/Shanghai` 自然日为准。
- 每日赠送积分只限当天消耗；北京时间次日 00:00 后未使用部分失效。
- 每次消费先使用当天赠送积分，再使用永久积分。
- 会员权益有效期间不能购买当前会员档，也不能购买其他会员档，只允许自定义充值。
- 自定义充值只增加永久积分，不产生会员权益或每日赠送。
- 会员权益不叠加；有效期内不允许创建新的套餐订单。

## 2. 非目标

- 不改变自定义充值的 `1 元 = 100 积分` 规则。
- 不把兑换码、管理员调账或历史充值积分改成限时积分。
- 不引入可配置的会员天数；本次固定为 30 个自然日。
- 不依赖定时任务才能保证余额正确。
- 不修改已经支付并完成入账的历史订单。

## 3. 方案选择

采用“会员权益 + 每日独立积分桶 + 预扣来源分配”方案。

不采用直接往永久余额加赠送积分后再由午夜任务扣回的方式，因为任务停机、并发预扣和跨日退款会造成错账。也不采用账户单字段覆盖方式，因为无法可靠追踪每次冻结使用了赠送积分还是永久积分。

## 4. 时间与权益语义

- 所有业务日期使用 `Asia/Shanghai`，不使用服务器本地时区推断。
- 支付成功所在日期为权益第 1 天。
- 权益覆盖 30 个自然日，结束日期为开始日期加 30 天，左闭右开。
- 例如 2026-08-11 任意时刻支付成功：
  - 第 1 个积分桶有效至 2026-08-12 00:00。
  - 第 30 个积分桶对应 2026-09-09。
  - 2026-09-10 00:00 起会员权益失效。
- 不运行午夜任务也不影响正确性：读余额或预扣时只承认当前业务日期的积分桶，过期余额惰性标记为失效。

## 5. 数据模型

### 5.1 套餐

`recharge_packages`：

- 现有 `credits` 改为基础积分语义，值固定等于 `amount_cents`。
- 新增 `daily_bonus_credits INTEGER NOT NULL DEFAULT 0`。
- 新增 `benefit_version TEXT NOT NULL DEFAULT 'legacy_once'`，新套餐和迁移后的套餐使用 `daily_30d_v1`。

迁移现有套餐时：

- `daily_bonus_credits = max(credits - amount_cents, 0)`。
- `credits = amount_cents`。
- `benefit_version = 'daily_30d_v1'`。

### 5.2 订单快照

`tenant_recharge_orders` 新增：

- `base_credits`：支付成功后一次到账的永久积分。
- `daily_bonus_credits`：每天可领取额度。
- `benefit_days`：固定写入 30。
- `benefit_version`：下单时的权益版本快照。

部署前已经存在的待支付订单保持 `legacy_once`，到账时继续按其原 `credits` 一次性入账，避免支付条款在下单后变化。

### 5.3 会员权益

新增 `tenant_recharge_memberships`：

- `id`
- `tenant_id`
- `recharge_order_id`，唯一
- `package_id`、`package_name`
- `daily_bonus_credits`
- `starts_on`、`ends_on`，上海时区自然日，结束日不包含
- `status`：`active`、`expired`
- `created_at`、`updated_at`

同一租户同一时刻只能有一条有效权益。创建套餐订单和支付结算都要在事务中复核；有效权益存在时拒绝新套餐订单。

### 5.4 每日赠送积分桶

新增 `tenant_daily_bonus_buckets`：

- `id`
- `tenant_id`
- `membership_id`
- `benefit_date`
- `granted`
- `available`
- `held`
- `spent`
- `expired`
- `expires_at`
- `created_at`、`updated_at`
- 唯一键：`(membership_id, benefit_date)`

当前日积分桶在首次读取余额或首次消费时幂等创建。非当前日的 `available` 不计入可用余额，并在后续访问时惰性转入 `expired`。

### 5.5 预扣来源

新增 `tenant_usage_reservation_allocations`：

- `reservation_id`，唯一
- `tenant_id`
- `bonus_bucket_id`，可空
- `bonus_amount`
- `permanent_amount`
- `created_at`

每笔租户预扣必须记录资金来源，且满足：

`bonus_amount + permanent_amount = tenant_usage_reservations.amount`

## 6. 账户与消费规则

### 6.1 余额展示

对外账户字段保持兼容：

- `available = permanent_available + today_bonus_available`
- `held` 和 `spent` 继续表示账户总冻结、总消费。

同时增加不破坏旧调用方的明细字段：

- `permanent_available`
- `daily_bonus_available`
- `daily_bonus_expires_at`
- `membership_ends_on`

### 6.2 预扣

租户预扣在单个 SQLite immediate transaction 中执行：

1. 幂等读取现有 `tenant_id + operation_key` 预扣。
2. 惰性处理过期积分桶。
3. 幂等创建当前日积分桶。
4. 优先从 `daily_bonus_available` 预扣。
5. 不足部分从永久积分预扣。
6. 总额不足则整个事务回滚。
7. 写入预扣、流水及来源分配。

用户级旧账户路径保持原逻辑，仅租户路径接入每日赠送。

### 6.3 成功确认

- 永久部分与赠送部分都计入总 `spent`。
- 赠送积分从原日期积分桶的 `held` 转入 `spent`。
- 即使任务在次日才完成，也允许确认，因为前一天已经完成了有效预扣。

### 6.4 失败退款

- 永久部分始终退回永久可用余额。
- 赠送部分只有在其原积分桶仍处于有效自然日时才退回 `available`。
- 跨日退款时，赠送部分从 `held` 转入 `expired`，不能在次日复活。
- 重复确认或退款保持幂等。

## 7. 充值和购买门禁

### 7.1 套餐订单

创建套餐订单前检查：

- 当前租户没有有效会员权益。
- 当前租户没有另一笔仍可支付的套餐订单。
- 套餐启用且处于销售期。

支付回调继续校验签名、应用、商户、金额、交易号和订单幂等性。结算时再次检查订单快照，并原子完成：

1. 标记订单已支付。
2. 基础积分永久入账。
3. 创建 30 天会员权益。
4. 创建支付当日积分桶。

### 7.2 自定义充值

会员有效期内仍允许自定义充值。结算只增加永久积分，不修改会员期限和每日赠送额度。

## 8. 管理端和用户端

### 8.1 管理后台

套餐编辑字段改为：

- 售价（元）
- 基础积分（只读，根据售价按 `1 元 = 100 积分` 计算）
- 每日赠送积分
- 固定权益周期：30 天（只读说明）

保存时前后端都拒绝基础积分与售价换算不一致的请求。

### 8.2 用户充值中心

套餐卡片展示：

- `充值到账 X 永久积分`
- `连续 30 天，每天赠送 Y 积分`
- `每日赠送仅限当日使用，次日 00:00 清零`

会员有效时：

- 所有套餐购买按钮禁用。
- 显示会员到期日期和“有效期内不可重复购买会员档”。
- 自定义充值入口保持可用。

余额区域显示总可用积分，并提供永久积分和今日赠送剩余的明细。

## 9. API 与兼容

- 套餐 API 新增 `daily_bonus_credits`、`benefit_days`、`benefit_version`。
- 账户 API 新增每日赠送和会员明细字段，保留原 `available/held/spent`。
- 充值中心接口返回当前会员状态，前端不得仅靠本地状态决定能否购买。
- 订单创建后端门禁是最终裁决，绕过前端也不能重复购买。
- 历史已支付订单、兑换码、管理员调账和旧用户级积分账户不改变语义。

## 10. 审计与可观测性

积分交易记录增加以下可识别事件：

- 会员套餐基础积分到账
- 每日赠送额度生效
- 每日赠送额度过期
- 赠送积分消费
- 永久积分消费
- 跨日失败导致赠送退款转过期

日志和 API 不输出支付密钥或敏感回调内容。

## 11. 测试门禁

后端至少覆盖：

- 现有套餐迁移为基础积分和每日赠送积分。
- 新订单快照正确，旧待支付订单仍按旧规则结算。
- 支付回调重复到达不重复入账、不重复创建会员。
- 会员有效期内同档、跨档购买都被拒绝，自定义充值可用。
- 支付日为第 1 天，30 天边界和上海时区正确。
- 当日赠送优先消耗，剩余再扣永久积分。
- 午夜后未用赠送清零。
- 跨午夜已冻结任务可成功确认。
- 同日失败退回赠送额度，跨日失败不复活过期额度。
- 两连接并发预扣不超扣、不重复创建每日桶。
- 余额不足时所有账户、积分桶、预扣和流水均不变。

前端至少覆盖：

- 管理表单只允许配置每日赠送，基础积分由售价派生。
- 套餐卡片展示 30 天每日赠送与清零说明。
- 有效会员时所有套餐按钮禁用、自定义充值可用。
- 余额明细展示永久与当日赠送，不改变总余额兼容字段。

## 12. 发布与回滚

- 发布前从实时 `/opt/moli-drama/current` 克隆候选，不能用本地工作树覆盖生产。
- 先备份生产数据库，再运行幂等迁移和全量测试。
- 候选必须保留 `canvas-credit-callout-v1`，通过共享审计器和受保护激活脚本。
- 切换前核对其他会话、部署锁、活动任务、数据库健康和 AI 音乐进程隔离。
- 回滚应用版本时不能回滚已支付会员数据；旧版本无法理解每日积分桶，因此数据库迁移上线后只允许前滚修复，发布前必须完成候选验证。

## 13. 验收标准

完成不以按钮或单元测试为唯一证据。至少需要：

- 管理员创建/编辑套餐并在用户端看到准确权益文案。
- 测试租户完成一笔受控套餐支付结算或可信支付回调验收。
- 基础积分到账，首日赠送可用且优先消耗。
- 模拟或跨越上海时区日界线后，昨日未使用赠送不可用。
- 有效期内套餐购买被前后端共同禁止，自定义充值仍成功。
- 成功生成、明确失败退款和跨日退款三条链路账本一致。
