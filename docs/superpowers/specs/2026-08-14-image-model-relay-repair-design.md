# 图片模型精准路由、Token6688 结果解析与管理员中转关联设计

## 目标

在不覆盖其他会话改动、不触碰 AI 音乐服务、不扩大用户端供应商信息暴露的前提下，修复线上图片节点的三条独立故障链：

1. 画布选择 `gpt-image-2` 后，目录显示为可用，但生成阶段因配置类型不同而报“未配置图片模型”。
2. `gpt-image-2-2k` 仍显示为已验证，但 AIHubCC 已返回“无可用通道”。
3. `token6688-gpt-image-2` 收到 HTTP 成功响应后，适配器仅识别 URL，未覆盖 Base64 等同步结果格式，因此将实际可能已生成的结果记为未知。

同时在管理员 AI 配置表中增加“模型 → 中转站”关联展示，使每个模型都能追溯到其配置名称、中转站域名和配置 ID。

## 线上现状与证据边界

设计基于 2026-08-14 对线上 `/opt/moli-drama/current` 和共享 SQLite 数据库的只读检查：

- `gpt-image-2`：目录条目指向配置 `#4`，配置类型为 `storyboard_image`，供应商/Protocol 为 `aihubcc`，中转站为 `aihubcc.cc`；画布独立图片节点按 `image` 类型二次解析时返回空。
- `gpt-image-2-2k`：配置 `#2`，中转站同为 `aihubcc.cc`，仍是 active/default/verified 且价格启用；真实请求返回 `503 No available channel` 后已退回 40 积分。
- `token6688-gpt-image-2`：配置 `#11`，上游模型为 `gpt-image-2`，中转站为 `qd.token6688.com`。本日早些时候同一生产适配链曾成功生成可读 PNG，单独真实验证脚本也能识别 `b64_json`。
- 生成记录 `536`、`540`、`541` 均以“创建成功但未返回图片地址（结果未知）”结束；每笔 60 积分，共 180 积分仍为 `held`。

当时线上代码没有保存三次 HTTP 响应原文，因此不声称已证明这三次一定返回 `b64_json`。已证明的根因是生产适配器可识别的成功响应格式窄于已验证供应商响应范围。

## 方案选择

### 选中：精确配置路由 + 适配器补齐 + 失效模型下架

- 保留目录已经返回的 `config_id`，从画布选择、请求构建、计费解析、请求快照到运行时选配全链路传递。
- 对明确选择的目录配置，配置 ID 是路由身份，不再只根据模型名和画布节点类型二次猜测供应商。
- Token6688 同步图片响应解析范围与通用图片客户端已验证范围对齐。
- 已明确无通道的 `gpt-image-2-2k` 只下架自身，不停用同个中转站的其他配置或模型。

### 未选：复制 `storyboard_image` 配置为新 `image` 配置

这能短期避开类型不匹配，但会制造两条共享 Key/优先级/验证状态的重复配置，今后容易再次串路由，不采用。

### 未选：从画布目录过滤所有 `storyboard_image`

这可以消除当前报错，但会丢失已真实验证的 `gpt-image-2` 能力，是功能退化，不采用。

## 详细设计

### 1. 模型目录与生成请求

- 用户端目录条目继续使用现有 `model` 作为对外选择值。目录 API 保留现有的不透明 `config_id` 供内部路由，但普通用户界面不渲染配置 ID，也不新增中转站名称或域名。
- 前端内部模型选项保留目录的 `config_id`、`provider` 和原始模型元数据，但只将 `config_id` 作为生成请求的不可见路由字段。
- 后端收到 `config_id` 后必须校验：配置存在、未删除、已启用、已通过真实生成门禁，并且配置包含请求模型。任一不符合都拒绝，不回退到同名其他供应商。
- 计费预估、预扣保留、`image_generations.request_snapshot`、异步任务执行共用同一 `config_id`，防止前端与后端选到不同中转站。
- 兼容旧请求：没有 `config_id` 时继续使用现有模型解析，但新画布目录选择必须携带精确配置。

### 2. Token6688 同步图片结果

成功 HTTP 响应按以下顺序解析首张图片：

1. `data[0].url`
2. `data[0].image_url`
3. `data[0].b64_json`
4. 顶层 `image_url`
5. `result.url`
6. 顶层 `images[0]`（可为 data URL 或纯 Base64）

Base64 会转换成带 MIME 的 data URL，然后进入现有 `uploadService.downloadImageToLocal` 落盘、格式验证和静态资产路径链路。不把 Base64 原文、签名 URL 或 Key 写入日志。

若 HTTP 成功但仍无可读图片，日志只记录：

- `image_gen_id`
- 请求模型
- HTTP 状态
- 响应字节数
- 顶层字段名
- `data[0]` 字段名
- 若存在，上游请求/任务编号

返回结果仍是 `indeterminate`，计费保持 `held`，系统不自动重试、不自动确认扣费、不自动退款。

### 3. `gpt-image-2-2k` 下架

生产数据变更只针对：

- `ai_service_configs.id = 2`：设为不活跃、非默认，验证状态标为失败，保留配置和历史字段供管理员审计。
- `model_credit_prices.model = 'gpt-image-2-2k'`：设为禁用，保留原价格数据。

变更在共享 `deploy.lock` 中使用带旧值条件的事务 SQL 执行，影响行数不符合预期即回滚。不修改配置 `#4`、`#11` 或同中转站下其他模型。

恢复 `gpt-image-2-2k` 必须使用目标 Key 完成一次新的真实生成，等待成功终态，验证结果文件可读，再由独立变更重新启用。

### 4. 管理员后台 A 方案

在现有 AI 配置表增加“模型 → 中转站”列。每个配置的模型数组逐项显示：

`<模型标识> → <配置名称> · <Base URL hostname> · #<配置 ID>`

例如：

`token6688-gpt-image-2 → Token6688 图片 · qd.token6688.com · #11`

展示规则：

- 仅复用现有管理员配置 API 已返回的 `id`、`name`、`model`、`provider`、`base_url`；不新建数据表，不重复存储域名。
- 域名在前端从 `base_url` 安全解析；非标准 URL 则显示“未识别域名”，不抛出页面异常。
- 列表不显示 API Key、签名参数或 Base URL 的 query/fragment。
- 该列只存在于已有平台管理员权限门禁下的 AI 配置页。
- 普通用户 API 不增加中转站名称或域名；画布模型下拉、生成请求响应和生成结果页不渲染中转站、供应商或配置 ID。

## 计费与历史未知任务

- 明确上游失败：保持现有终态退款行为。
- 上游成功但平台无法确认资产：标记结果未知并保持 `held`。
- 记录 `536`、`540`、`541` 不随代码发布自动修改。必须先在 Token6688 供应商记录中核对是否生成/扣费，再单独执行对账。
- 本次修复验证不自动再次提交相同付费请求。代码、单元和集成测试通过后，如需真实生成验收，必须单独获得一次提交授权。

## 测试设计

实现必须遵循 TDD，每个生产行为先看到相应测试因功能缺失而失败。

### 后端

- Token6688 `data[0].b64_json` 返回可用 data URL。
- Token6688 顶层 `images[0]` 支持纯 Base64 和 data URL。
- Token6688 既有 URL 返回格式不回归。
- Token6688 无可读资产时只记安全字段摘要，不记录 Base64/密钥/签名 URL。
- 画布图片请求携带 `config_id=4` 时，计费、请求快照和运行时都解析到配置 `#4`，不受 `storyboard_image` 与 `image` 字面类型差异影响。
- 配置 ID 与模型不匹配、配置被停用或未通过门禁时直接拒绝，不串到其他同名供应商。
- 公开图片模型 API 不返回中转站域名或 API Key。

### 前端

- 目录规范化保留 `config_id`，图片生成请求携带对应 ID。
- 管理员配置表为每个模型显示配置名、域名和配置 ID。
- 非法 Base URL 不导致组件渲染失败。
- 普通用户画布模型标签不出现 `aihubcc.cc`、`qd.token6688.com`或 `#<config_id>`。

### 完整回归

- 后端全量 `npm test`。
- 前端 Node 测试集。
- 画布后端集成 E2E：目录选项到请求 payload 的 `config_id` 绑定。
- 管理员页面可见性与普通用户页面不暴露回归。
- 前端生产构建。
- `canvas-credit-callout-v1`、图片节点发布审计、增量发布范围审计。

## 发布设计

1. 实现完成后提交任务分支，推送 PR，等待 CI 通过并合入 `main`。
2. 发布前通过 SSH 重新读取实时 `/opt/moli-drama/current`、`deploy.lock`、活动生成任务、队列、健康状态和 AI 音乐 PID。
3. 候选必须从当时实时 `current` 克隆，只覆盖已审计的改动文件和受控数据变更脚本。
4. 发布 allowlist 与 manifest 在构建前后均运行增量范围审计，范围外差异直接中止。
5. 备份共享 SQLite，验证备份完整性，然后在 `deploy.lock` 内执行针对配置 `#2` 和对应价格的条件更新。
6. 只允许使用共享 `activate-protected-release.sh CANDIDATE EXPECTED_CURRENT` 激活，不直接替换 `current`。
7. 激活后验证线上健康、数据库完整性、目录可见性、普通用户不暴露、管理员关联列、空队列与 AI 音乐 PID 不变。

## 非目标

- 不向普通用户显示供应商或中转站。
- 不为了规避类型问题创建重复 AI 配置。
- 不改名或重定价其他已通过的图片模型。
- 不修改其他会话正在开发的 Fumin/转绘/视频文件。
- 不自动处理历史 180 冻结积分。
- 不修改、重启或发布 `/opt/moli-mama` AI 音乐项目。

## 成功标准

- `gpt-image-2` 的目录配置身份从前端到运行时保持一致，不再报“未配置图片模型”。
- Token6688 的 URL/Base64 成功格式均能进入本地落盘链，无资产格式仍按结果未知处理。
- `gpt-image-2-2k` 不再出现在普通用户目录，但管理员仍能看到其历史配置、中转站和失败状态。
- 管理员能逐模型看到配置名、中转站域名和配置 ID；普通用户界面不显示这些信息，公开 API 不增加中转站名称或域名。
- 所有针对性测试、后端全量测试、前端测试与生产构建通过。
- PR/CI/合入、最新线上候选、增量审计、共享受保护激活、线上健康和 AI 音乐隔离全部留有可核对证据。
