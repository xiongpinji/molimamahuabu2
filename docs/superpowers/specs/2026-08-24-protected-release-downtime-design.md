# 共享受保护发布低停机窗口设计

## 状态

- 设计日期：2026-08-24
- 设计状态：方案已获用户批准，等待书面规格复核
- Git 基线：`523ac09eeed7da427cf69d3c91cd16eb78e29994`
- 后续交付：独立安全实现计划、独立安全 PR、独立人工审查与轮换授权
- 本文档只定义设计，不授权修改共享门禁、推送、部署、生产写入、服务重启或付费调用。

## 背景与已确认事实

当前共享激活器在停止 `moli-drama.service` 后执行一次完整 `candidate_tree_hash`。该函数遍历候选
目录，对每个普通文件计算 SHA-256，并对符号链接目标再次读取。候选包含前后端依赖和构建产物时，
这次扫描会显著扩大生产不可用窗口。

2026-08-24 的一次受保护激活中，服务从 15:02:42 停止，到 15:05:16 才重新启动，15:05:18
恢复健康。期间 Nginx 记录了 11 个 `502`，其中 8 个是画布布局保存。激活最终成功，说明主要问题
不是新版本启动失败，而是停机区间包含了本可在停服前完成的全树哈希。

当前门禁基线测试 37/37 通过，并已保护：部署锁、实时 current CAS、SQLite 备份与完整性检查、
活动任务阻断、候选树权限与哈希、生产环境固定、健康与日志、失败回滚、AI 音乐进程隔离。

## 目标

1. 将所有耗时的完整候选树读取移出 `systemctl stop` 到服务重新启动之间的停机区间。
2. 保留初始、验证后、切换前和健康后的四次候选树哈希合同。
3. 停机区间仍执行活动任务、current CAS、生产环境、候选锁定状态和证据树的快速检查。
4. 任一检查失败时保持或恢复旧版本，并确认旧版本健康。
5. 在审计文件记录各阶段耗时，让后续停机预算可量化回归。
6. 不降低数据库备份、回滚、日志、权限、供应商证据或 AI 音乐隔离门禁。

## 非目标

- 不实现真正的双进程、蓝绿、容器或负载均衡零停机发布。
- 不直接替换 `/opt/moli-drama/current`，不绕过共享激活器。
- 不允许业务候选携带并覆盖共享门禁。
- 不删除四次完整哈希，不用目录修改时间代替内容哈希。
- 不减少健康检查、日志检查、数据库备份或活动任务检查。
- 不触碰、停止、重启或部署 `/opt/moli-mama` AI 音乐。
- 不把本安全变更与画布自动保存或其他业务代码放入同一个实现 PR。

## 方案选择与安全权衡

采用“停服前完成切换前完整哈希，停服后只做快速锁定检查”。

未采用以下方案：

- **删除切换前哈希：** 会失去验证后到切换前的候选篡改检测。
- **停止服务后并行哈希与其他检查：** 仍把完整扫描留在停机窗口，最坏耗时不变。
- **直接原子切换后再检查：** 未经切换前确认的候选可能先运行，削弱 fail-closed。
- **立即建设蓝绿发布：** 需要端口、反向代理、数据库迁移兼容和双实例任务互斥，范围远超本次故障。

完整哈希提前后，从该哈希完成到原子切换之间仍存在一个短窗口。安全边界是：候选及解析后的树均为
`root:root`，group/other 不可写；部署锁阻止协作发布并发；current 使用 CAS；停服后再次验证候选根、
证据树和固定环境；健康后第四次完整哈希会捕获任何内容漂移并回滚。拥有 root 权限的恶意进程仍可
绕过文件权限，这属于主机 root 已失陷，不是发布脚本能够单独解决的威胁模型。

相较当前实现，哈希完成到切换之间的时间会增加一次快速停服/检查时长，但候选被未授权普通用户
篡改的能力没有增加；root 级漂移会在健康后被发现并回滚。该权衡以显著缩短用户可见停机为目标，
且不删除任何已有完整哈希证据。

## 目标执行顺序

### 阶段 A：锁内、服务在线的完整预检

1. 取得共享部署锁。
2. 校验实时 current 等于调用方传入的 `EXPECTED_CURRENT`。
3. 校验共享验证器、证据树和候选树权限。
4. 计算初始候选树哈希。
5. 运行 UI、顺序和外部模型证据验证器。
6. 再次校验证据树、候选权限并计算验证后完整哈希；必须与初始哈希一致。
7. 若为 verify-only，到此退出，绝不备份、停服或切换。
8. 校验固定 `production.env`，读取安全配置并初始化根权限审计文件。
9. 快照 AI 音乐进程。
10. 创建并验证生产 SQLite 备份。
11. 确认没有活动生成任务，current CAS 与 `production.env` 均未漂移。
12. 再次校验证据树和候选权限，计算“切换前完整哈希”；必须与初始哈希一致。

步骤 12 必须是停服前最后一个可能全量读取候选内容的操作。完整哈希成功后立即进入停机阶段，
中间不得插入构建、安装依赖、迁移、网络验证或其他不受时限约束的动作。

### 阶段 B：最小停机区间

停机区间从 `systemctl stop moli-drama.service` 调用开始，到新版本
`systemctl restart moli-drama.service` 返回为止。只允许按顺序执行：

1. 停止 `moli-drama.service`；停止失败进入既有回滚恢复流程。
2. 再次确认没有活动或处理中任务。
3. 再次确认 current CAS 未漂移。
4. 校验固定证据树、候选根及解析树仍为 `root:root` 且 group/other 不可写。
5. 确认 `production.env` 内容哈希未变。
6. 原子将 current 指向候选。
7. 立即重新启动 `moli-drama.service`。

该区间禁止调用 `candidate_tree_hash`、构建、安装依赖、执行迁移、调用供应商、运行浏览器或读取完整
候选文件内容。SQLite 迁移仍由新服务按既有启动合同执行；若启动或迁移失败，走既有回滚。

### 阶段 C：服务启动后的验证与提交

1. 等待内部健康检查成功。
2. 收集本次启动日志，并拒绝 fatal、未处理异常、端口占用、模块缺失、语法、数据库损坏或迁移失败。
3. 确认 current 仍指向候选。
4. 再次校验证据树和候选权限。
5. 计算健康后完整候选树哈希；若与初始哈希不一致，回滚旧 current、重启旧服务并确认健康。
6. 再次快照 AI 音乐进程；任何漂移均回滚，但不得操作 AI 音乐服务。
7. 写入成功审计，标记激活提交。

## 快速候选锁定检查

停服后的候选检查必须是一个职责明确的函数，不得间接调用完整哈希。它只验证：

- 候选路径仍解析在固定 releases 根目录内；
- 候选根目录仍为 `root:root` 且 group/other 不可写；
- 已知符号链接仍解析在 releases 根目录内；
- 解析项仍为 `root:root` 且 group/other 不可写；
- 固定共享证据树仍满足现有根权限合同。

实现计划必须评估现有 `assert_candidate_tree_secure` 的运行成本。若该函数在真实候选上仍接近完整哈希
成本，应拆出只覆盖上述锁定事实的快速检查；不得用函数重命名掩盖同样的全树内容扫描。

## 阶段耗时审计

审计文件新增单调时钟耗时，不使用墙上时间差计算持续时间。至少记录：

- `preflight_verification_ms`；
- `database_backup_ms`；
- `pre_switch_hash_ms`；
- `service_stop_ms`；
- `post_stop_checks_ms`；
- `service_restart_ms`；
- `health_wait_ms`；
- `post_health_hash_ms`；
- `downtime_window_ms`。

审计不得记录生产环境值、数据库内容、Key、Token、用户数据或完整命令行。阶段开始后即使失败，也要
在失败/回滚审计中保留已经完成阶段的耗时。

`downtime_window_ms` 只表示脚本控制的 stop 到 restart 返回时间，不冒充公网完全恢复时间。生产验收
仍需单独记录健康就绪和公网入口恢复时间。

## 失败与回滚合同

- 停服前任一失败：不触碰服务和 current，直接退出。
- stop 失败、停服后活动任务、CAS 漂移、环境漂移或锁定检查失败：确保 current 恢复为
  `EXPECTED_CURRENT`，启动旧服务并确认旧健康。
- 新版本健康、日志、健康后哈希或 AI 音乐快照失败：恢复旧 current，重启旧服务并确认健康。
- 旧版本也无法恢复健康：保留失败审计并以非零退出，不继续尝试其他候选。
- 任何未知状态不得自动再次执行激活。

数据库备份、备份完整性、回滚 current、旧版本健康确认和根权限审计沿用现有实现，不能因缩短停机
而简化。

## TDD 验收

### 顺序与静态合同

1. 源码仍包含初始、验证后、切换前、健康后四次 `candidate_tree_hash`。
2. 切换前完整哈希出现在 `systemctl stop` 之前。
3. `systemctl stop` 与新版本 `systemctl restart` 之间不存在 `candidate_tree_hash` 或完整内容扫描。
4. 停服区间保留活动任务、current CAS、证据树、候选锁定状态和环境哈希检查。
5. verify-only 路径不创建备份、不停服、不切换。
6. 审计包含所有约定阶段耗时且不泄露敏感值。

### Linux 激活 fixture

1. 候选在初始到验证后发生变化，停服前失败。
2. 候选在验证后到切换前完整哈希之间发生变化，停服前失败。
3. 停服后 current 漂移、活动任务出现、环境变化或权限变化，恢复旧版本并健康。
4. 新版本健康失败、fatal 日志、健康后候选漂移或 AI 音乐漂移，完整回滚。
5. 数据库备份失败或损坏在停服前失败。
6. 正常激活的服务操作顺序仍为 `stop moli-drama`、`restart moli-drama`，不出现 AI 音乐操作。
7. 在测试替身中让每次完整哈希固定延迟，证明该延迟不会计入 stop 到 restart 的停机区间。
8. 现有共享门禁 37 项基线全部继续通过，并新增上述回归。

### 性能验收

使用与生产候选文件数量、构建产物和依赖规模相近的本地 Linux fixture，至少运行 3 次：

- 记录总激活、切换前哈希、stop 到 restart、健康就绪和健康后哈希耗时；
- stop 到 restart 区间不得包含完整哈希耗时；
- 三次结果都满足同一顺序合同，不能只选择最快一次；
- 性能结果只证明候选可进入生产审查，不替代真实生产激活授权。

不在设计阶段承诺一个未经同环境测量的绝对秒数。实施计划应先以基线 fixture 建立预算，再由用户
批准生产激活前的停机目标。

## 独立安全变更与轮换

共享门禁位于 `/opt/moli-drama/shared/release-guard`，普通 release 候选不得替换它。因此后续交付必须：

1. 只在独立安全分支和独立 PR 修改激活器、轮换脚本及门禁测试；
2. 固定并审查已安装旧激活器 SHA-256 和拟安装新激活器 SHA-256；
3. 使用根权限、固定路径、原子替换和失败回滚的门禁轮换流程；
4. 轮换前重新读取实时已安装哈希，不匹配已审查旧哈希时停止；
5. 轮换本身与任何业务候选激活分开授权；
6. 轮换后先执行 verify-only 和无付费健康验证，再另行申请业务候选激活。

画布自动保存改动不得依赖共享门禁轮换才可合入；共享门禁改动也不得把画布业务文件纳入安全 PR。

## 生产发布边界

即使独立安全 PR 已合入，也不代表共享门禁已轮换。生产轮换前必须：

- 重新协调其他会话，确认没有并发候选、生产数据库写入或激活；
- 重新读取实时 current、deploy lock、已安装门禁哈希和 AI 音乐进程；
- 备份共享门禁和生产 SQLite，并验证备份；
- 取得“轮换共享门禁”的单独明确授权；
- 轮换失败时恢复旧门禁，不删除任何已有候选；
- 不执行供应商请求、不付费、不修改模型或用户积分数据。

本文档不授予任何生产权限。

## 完成标准

- 四次完整候选哈希仍存在且比较同一初始哈希；
- stop 到 restart 之间没有完整候选内容扫描；
- 数据库备份、活动任务、CAS、环境、健康、日志、回滚和 AI 音乐隔离全部保持；
- 阶段耗时可审计，且不泄露敏感信息；
- 现有 37 项门禁测试和新增顺序、失败、回滚、性能测试全部通过；
- 安全 PR、共享门禁轮换和业务候选激活分别审查、分别授权。

满足这些条件只代表共享门禁新版本可申请人工轮换，不代表画布自动保存业务改动或任一生产候选已经
上线。
