# 整集转绘隔离多视频模型回退设计

## 1. 目标与已确认基线

本规格在 PR #217 当前已审计 HEAD `823808b5f307c4d54e21eb63a881192c4ad2b90f` 上，为 28 个固定 5 秒整集生成单元增加隔离的多模型回退能力。目标是在不改动线上模型、生产数据和部署状态的前提下，先用首单元 `shot-01.part-01` 依次验证四条兼容线路，并让首个完整通过验收的模型独占后续 27 个单元的整集生成。

已有 r23 状态和产物只作为历史证据，不覆盖、不复用、不从其中续跑。新运行必须使用全新本地隔离目录。

## 2. 执行边界

- 只修改 PR #217 分支内的本地代码、测试、规格和验收证据；不合并、不部署、不重启。
- 不读取、不写入生产数据库，不修改生产 `ai_service_configs`、线上模型目录、共享验证器或共享证据。
- 供应商 Key 只能从显式本地 Key 文件或当前进程环境变量读取，仅用于本次隔离验收；不持久化、不记录、不输出 Key 原文。
- 某条线路缺少 Key 时，必须在上传和生成请求之前标记为 `skipped_missing_key`，该线路保持 0 上传、0 生成提交。
- 付费阶段只能在新 HEAD 推送到 PR #217，且该精确 HEAD 的 Hosted CI 4/4 全绿后开始。

## 3. 方案选择

采用方案 A：“路由状态完全隔离，整集只使用首个通过的模型”。

- 每条模型线路使用独立状态子目录、提交计数器和防重键，不在不同模型间共享任务 ID 或未决状态。
- 四条线路只在首单元竞选；一旦某条线路通过媒体、音轨、英文对白、角色和时长验收，后续 27 个单元必须全部继续使用该线路。
- 不采用逐单元跨模型回退，因为这会破坏整集的角色、画风、声线和运镜一致性。
- 不采用 Fumin 单线重试，因为 r23 已证明单一线路的明确失败会阻断整集，而本次授权已给出确定的兼容回退顺序。

## 4. 固定路由与能力合同

路由顺序不可配置、不可跳过已具备 Key 的前置线路：

1. `fumin-fast`：Fumin，模型 `fumin-seedance-2.0-fast`（供应商模型 `seedance-2.0-fast`）。
2. `toapis-fast`：ToAPIs，模型 `seedance-2-fast`。
3. `toapis-wan3`：ToAPIs，模型 `wan3.0-video`。
4. `feituo-seedance-2.5`：飞拓，模型 `xuan-seedance-2.5`。

四条路由均必须在当前代码合同中支持 480p、9:16、5 秒和所需参考素材才可提交。Fumin Fast、ToAPIs Fast 和 ToAPIs Wan3 还必须显式发送其已有协议的“生成音频”字段。飞拓 Seedance 2.5 当前协议只能证明可传入音频参考，没有独立的输出音频开关；因此它在本轮是明确标记的实验线路，请求必须带英文有声提示和音频参考，只有返回成品真实存在音轨并通过双 ASR 后才能胜出，不得预先宣称已验证有声能力。未通过对应本地合同校验的模型不得动态加入。ToAPIs Mini、NewAPI 16:9 线路、USMercari 16:9 线路、不支持音频的灵境线路不在本轮范围内。

## 5. 组件设计

### 5.1 路由注册表

新增纯函数路由注册表，固定记录路由 ID、供应商、模型、Key 来源标识、能力合同和顺序。注册表只服务本地验收运行器，不导出到前端模型目录，不修改通用生产路由。

### 5.2 供应商适配器

- Fumin 适配器保留原 Mini 默认值，只增加由隔离运行器显式注入已允许 Fumin 模型的能力；未注入时既有行为不变。
- ToAPIs Fast、ToAPIs Wan3 和飞拓 Seedance 2.5 分别复用已有供应商客户端的请求构建、状态解析和“未知”错误语义，不复制新的协议实现。
- 媒体下载、ffprobe、双 ASR、英文对白核对、角色核对、精确裁剪和整集合成继续复用现有 Fumin 整集媒体管线，避免四份验收逻辑漂移。
- 先完成 Key 和能力预检，再上传参考。适配器必须优先使用相应供应商已支持的参考上传；若目标 API 只接受 HTTPS 参考且无原生上传，可使用本轮已授权的 Fumin 文件上传作为传输层，但必须在状态中分开记录“上传供应商”和“生成供应商”，且 Fumin Key 缺失时在上传前跳过该路由。

### 5.3 全局调度器

新增一个本地隔离调度器，在运行根目录下写入父 manifest 和每路由独立子目录。父 manifest 至少绑定：

- 精确 40 位 Git HEAD、整集包哈希、执行计划哈希和 28 个单元清单；
- 固定路由顺序、每路由模型标识、状态子目录和已用提交数；
- 全局提交数、当前路由、获胜路由、停止原因和每份结果的 SHA-256；
- 脱敏的供应商终态原因，但不包含 Key、Authorization 头或完整请求体。

所有状态使用原子写入。已存在且非空的运行目录不得被覆盖或复用。子运行器继续使用已有确定性单元防重键，父调度器再执行全局计数和模型选择门禁。

## 6. 状态机与提交上限

1. 载入并校验 28 单元包，生成全新运行根目录；任一本地条件不通过时保持 0 上传、0 生成提交。
2. 按固定顺序检查路由 Key 和能力；缺 Key 路由零提交跳过。
3. 对当前路由的 `shot-01.part-01` 最多执行 1 次生成提交。
4. 只有供应商返回可确认的失败终态且本地已保存脱敏失败证据时，才可封存当前路由并转入下一条。
5. 上传、提交、轮询、下载、结果解析或运输状态任一未知，立即把全局状态置为 `needs_attention` 并停止，不得切换模型或再次提交。
6. 供应商返回完成，但产物不可读、媒体、音轨、目标英文对白、时长或角色一致性验收不通过时，同样全局停止；这不等于“供应商明确失败”，不得用另一模型制造第二份已付费产物。
7. 首单元通过后锁定获胜路由，按计划顺序生成其余 27 个单元；任一后续单元失败或未知均停止，不再切换模型。
8. 四条竞选线路最多各消耗 1 次首单元提交；最坏情况下前三条明确失败 3 次，第四条通过并完成 28 个单元，因此全局生成提交硬上限为 31。

## 7. 结果验收与交付合同

首单元和其余 27 个单元使用相同验收链：原始 MP4 可读、480p 竖屏、约 5 秒、存在音轨、双 ASR 为 en-US 英文且与批准台词一致、角色映射与当前国家化名称一致。每份原始结果、裁剪结果、父镜头和最终整集均记录 SHA-256。

交付只有一个成功终态：28 个单元均由同一获胜路由完成并通过验收，合成的 24 镜整集与蓝图顺序和 68,733ms 时间线一致，有连续音轨，15 段对白均为批准英文，不含中文对白或未批准对白。

## 8. TDD 与验证门禁

实现顺序必须先红后绿，至少覆盖：

1. 路由顺序和四个精确模型合同不可漂移。
2. 缺 Key 路由 0 上传、0 生成提交并继续下一路由。
3. 首单元明确失败可转下一路由；任一未知或产物验收失败立即全局停止。
4. 首个通过的模型锁定后续 27 个单元，不得混用模型。
5. 同一路由、同一单元不可重复提交，全局计数永不超过 31。
6. 保存脱敏供应商终态原因，不泄露 Key 或请求授权头。
7. 使用伪 HTTP 适配器完成四路由竞选和 28 单元整集零供应商端到端测试。
8. 新增代码纳入 `redraw.episode-blueprint-first` 功能锁，保留已有解锁历史，并通过所有受影响回归、前端构建、发布范围校验和 PR #217 Hosted CI 4/4。

## 9. 实施与真实执行顺序

1. 本规格书面审批后，编写详细实现计划。
2. 按 TDD 实现路由注册表、供应商适配器、全局调度器、状态证据和功能锁。
3. 运行受影响回归、零供应商端到端测试、前端构建和功能锁/发布范围校验。
4. 把实现提交并推送到 PR #217，锁定新的精确 HEAD。
5. 等待该 HEAD 的 Hosted CI 4/4 全绿；未全绿不得使用任何供应商 Key。
6. 创建全新本地隔离运行目录，按固定顺序执行最多 31 次生成提交。
7. 只有完整整集通过时才交付最终 MP4、二进制哈希、单元结果清单、台词/媒体验收和脱敏计费状态。任一中止情形均保留不可变的本地证据并如实报告，不冒充为整集交付。
