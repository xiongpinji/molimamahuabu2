# 平台稳定性与一次性验收锁定总实施计划

> **执行要求：** 使用 `executing-plans` 按阶段执行；任何阶段都不得跳过红灯复现、绿灯回归、全量测试和锁定清单。若用户明确选择子代理驱动，再改用 `subagent-driven-development`，并保持每个任务独立审查。

**目标：** 建立图片、视频、文本统一的安全容灾和管理员控制面，并依次对画布、短剧工厂、剧本分析完成一次性“验证—必要修复—锁定”。

**基线：** `origin/main@8f9a66cd`；隔离分支 `codex/platform-stability-one-pass-lock-20260815`；设计文档 `docs/superpowers/specs/2026-08-15-platform-stability-one-pass-lock-design.md`。

**不可突破的边界：** 不把模型列表或连接测试当可用性证据；不自动重试可能已受理的请求；不自动修改用户提示词；不向普通用户暴露中转站；不在未获得单次授权时调用付费模型；不从本地旧工作树整体覆盖生产；不触碰 AI 音乐服务。

## 阶段顺序

| 阶段 | 独立计划 | 进入条件 | 退出条件 |
| --- | --- | --- | --- |
| 1. 稳定性底座 | `2026-08-15-platform-stability-foundation.md` | 当前基线全绿 | 安全容灾、未知态、计费、管理员日志、CI 门禁全部通过 |
| 2. 画布一次性验收 | 阶段 1 合入后，从届时最新 `main` 编写 `platform-stability-canvas-lock.md` | 阶段 1 已发布并回读；画布功能清单已从真实入口生成 | 每项 `pass/fail/blocked/not_applicable` 有证据；缺陷修复后锁定 |
| 3. 短剧工厂一次性验收 | 阶段 2 合入后，从届时最新 `main` 编写 `platform-stability-short-drama-lock.md` | 画布已锁定；工厂功能清单已从真实入口生成 | 工厂与画布回读通过；每项锁定 |
| 4. 剧本分析一次性验收 | 阶段 3 合入后，从届时最新 `main` 编写 `platform-stability-script-analysis-lock.md` | 前两板块已锁定；分析功能清单已从真实入口生成 | 分析、导入工厂、投影画布全链回读；每项锁定 |

后三个阶段必须在开始时重新生成精确计划。原因是“本轮实际验证后发现的缺陷”目前尚未知；提前写假设性修复文件会违反精准修改原则。没有缺陷的功能不改业务代码，只补证据与保护测试。

## 每个业务板块的固定执行模板

### 任务 A：从真实入口生成完整功能清单

**读取：**

- 前端路由、页面、可见按钮、菜单、快捷键、上下文菜单和对话框。
- 后端路由、服务、任务、素材、积分和管理员接口。
- 当前线上真实入口及当前生产 release 版本。

**产物：** `docs/verification/platform-stability/<module>/feature-inventory.json`

每条记录固定包含：`feature_id`、入口、前置条件、操作、预期 UI、预期后端状态、预期素材、预期积分、测试路径、付费需求、状态。状态只允许 `pass`、`fail`、`blocked`、`not_applicable`。

### 任务 B：逐项执行无付费合同、集成和浏览器验证

1. 先运行该板块已有 Node/Playwright 测试并保存完整日志。
2. 在真实浏览器逐按钮执行，不能用“页面能打开”代替交互通过。
3. 检查数据库写回、刷新恢复、重复点击、权限、租户和积分。
4. 无缺陷项立即写入 `locked_pass`，标记“未修改业务代码”。
5. 缺陷项保存稳定复现步骤、截图/日志、请求号和安全错误摘要。

### 任务 C：缺陷按 TDD 精准修复

对每一个 `fail`：

1. 新增最小失败测试，单独运行并确认红灯原因与缺陷一致。
2. 只修改能直接追溯到该缺陷的文件。
3. 单测绿灯后运行该功能的后端集成与 Playwright。
4. 运行板块回归，不能改变已锁定项。
5. 记录修复提交并转为 `locked_fixed`。

每个缺陷独立提交：

```bash
git add <该缺陷直接相关文件>
git commit -m "fix(<板块>): <缺陷的用户可见行为>"
```

### 任务 D：真实供应商验证门禁

只有需要真实供应商才能闭环的条目进入此任务。先完成全部无付费准备，再向用户汇报：供应商、逻辑模型、请求参数、次数、用户积分、供应商成本、余额和是否存在未知任务。取得一次提交授权后只提交一次。

必须同时取得：供应商成功终态、可读取产物、业务记录回写、前端可打开/下载、积分正确结算。任何链接不可读或结果未知均为 `blocked/needs_attention`，禁止自动重提。

### 任务 E：锁定清单与 CI 门禁

**修改：**

- `docs/verification/platform-stability/feature-lock-manifest.json`
- 当前板块直接对应的保护测试。

运行：

```bash
cd backend-node
npm run audit:feature-lock
npm test
cd ../frontweb
node --test test/*.test.js
npm run build
```

期望：全部退出码为 0；锁定项的证据文件存在；受保护路径发生变化但没有解锁记录时审计失败。

### 任务 F：阶段独立 PR 与受保护增量发布

1. 确认工作树无其他会话未提交重叠修改。
2. 推送阶段分支、创建独立 PR、等待 CI、审查并合入 `main`。
3. 部署前通过 SSH 读取实时 `/opt/moli-drama/current`、`deploy.lock`、活动任务、健康、日志和 AI 音乐 PID。
4. 从实时 `current` 克隆候选，只覆盖本阶段 release scope allowlist。
5. 执行数据库备份、增量范围审计、受保护合同审计和候选构建。
6. 只用 `activate-protected-release.sh CANDIDATE EXPECTED_CURRENT` 激活。
7. 激活后回读版本、健康、日志、板块无付费冒烟、数据库和 AI 音乐 PID。

发布、推送、PR、真实供应商调用均是独立权限边界；执行计划本身不自动授予这些权限。

## 总体验收

- 三个板块所有功能都有本轮证据，不依赖历史总结。
- 同模型明确未受理故障能切换；可能已受理/结果未知绝不重提。
- 可读取产物与业务回写成功后才扣积分。
- 管理员可追溯供应商，普通用户接口和页面无供应商信息。
- 无缺陷功能没有无关业务改动；有缺陷功能有红灯、修复、绿灯和锁定提交。
- 所有阶段独立 PR、独立 release scope、独立生产回读，未影响其他会话或 AI 音乐。
