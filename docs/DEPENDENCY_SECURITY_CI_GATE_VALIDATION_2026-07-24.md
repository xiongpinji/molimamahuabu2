# 依赖安全持续门禁验证（2026-07-24）

## 结论

本地实现与回归通过，可以提交 PR 进入 GitHub Actions 验收；在 PR 的新增门禁与既有回归检查全部通过前，不宣称该阶段已合并或可发布。

## 红灯证据

1. 新增策略测试首次运行共 3 项失败：
   - 缺少 `dependency-security.yml`；
   - 前端端到端与发布工作流仍使用 Node.js 22；
   - 后端与桌面 npm 配置关闭 TLS 校验。
2. 首次执行三个子项目的官方生产依赖审计：
   - `backend-node`：0；
   - `frontweb`：0；
   - `desktop`：6 个高危、1 个严重。
3. 新增锁文件镜像主机覆盖断言后，策略测试因三个安装步骤均未设置 `replace-registry-host=always` 而失败。

## 修复内容

- 新增每个 PR、`main` 推送和手动触发都会运行的生产依赖门禁。
- 三个子项目均执行无安装脚本的干净安装及高危阈值生产审计。
- CI 审计明确使用 npm 官方注册表；后端与桌面安装覆盖历史镜像主机。
- 前端保留带 integrity 的 `three` 定制 tarball 锁定地址，该制品在 npm 官方仓库不存在，强制替换会返回 404。
- 现有 Node 工作流统一到 Node.js 24。
- 删除发布流程中的 TLS 全局绕过，两个 npm 配置恢复证书校验。
- 桌面重复运行依赖对齐到后端已验证版本，并刷新锁文件。

首次 GitHub Actions 运行暴露了本地未覆盖的供应链例外：前端 `three` 定制 tarball 被强制改写到 npm 官方主机后返回 404。修复后仅后端和桌面使用 `replace-registry-host=always`，前端继续按锁文件地址及 integrity 安装，安全审计仍走 npm 官方接口。

本机工作树的预览服务占用原生 DLL/可执行文件，直接 `npm ci` 会触发 Windows `EPERM`。验证改在全新的临时目录中复制清单、锁文件和当前源码执行，避免停止正在运行的 3013/5679 演示服务。
